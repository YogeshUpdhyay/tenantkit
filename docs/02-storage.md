# 02 — Storage layer

The core talks only to repository interfaces. The host's database is plugged in through an adapter, and v1 ships two: in-memory for tests and SQLAlchemy for production.

## Purpose and responsibilities

- Define the domain models the package persists.
- Define abstract repository interfaces the services depend on.
- Provide an optional SQLAlchemy adapter that uses the host's engine and sessions.
- Provide an in-memory adapter for tests and prototyping.
- Provide a shared contract test suite every adapter must pass.

Out of scope: scoping the host's own business tables by tenant. The package tells the host who the tenant is through claims; filtering the host's data stays with the host.

## Domain models

Plain dataclasses in `domain/models.py`, with no database code.

| Model | Key fields | Notes |
| --- | --- | --- |
| `Admin` | id, email, password_hash, roles, impersonation_scope, is_active, created_at, updated_at | Super admins and other admin roles |
| `Tenant` | id, slug, attributes, login_policy, is_active, created_at, updated_at | `attributes` holds the dynamic fields from the tenant schema |
| `TenantUser` | id, tenant_id, email, password_hash, roles, is_active, created_at, updated_at | Email is globally unique: a user belongs to exactly one tenant |
| `LoginAttempt` | subject_type, subject_id, failed_count, locked_until | Backs the lockout rules from config |

- IDs are UUIDs generated by the package.
- Roles are stored as role names. Their permissions come from config, so changing config changes access without a data migration.
- `impersonation_scope` is stored as a mode (all, list, none) plus a list of tenant IDs.
- Refresh tokens are stateless signed tokens in v1, so nothing is stored for them. Revocation, deferred to a later version, would add a table.

## Repository interfaces

Defined as `typing.Protocol` classes in `storage/interfaces.py`. All methods are async.

```python
class TenantRepository(Protocol):
    async def create(self, tenant: Tenant) -> Tenant: ...
    async def get(self, tenant_id: UUID) -> Tenant | None: ...
    async def get_by_slug(self, slug: str) -> Tenant | None: ...
    async def list(self, *, active: bool | None = None, limit: int = 50, offset: int = 0) -> list[Tenant]: ...
    async def update(self, tenant: Tenant) -> Tenant: ...

class AdminRepository(Protocol): ...         # create, get, get_by_email, list, update
class TenantUserRepository(Protocol): ...    # create, get, get_by_email(email), list(tenant_id), update
class LoginAttemptRepository(Protocol): ...  # get, record_failure, reset

class Storage(Protocol):
    tenants: TenantRepository
    admins: AdminRepository
    tenant_users: TenantUserRepository
    login_attempts: LoginAttemptRepository
    def transaction(self) -> AsyncContextManager[None]: ...
    async def health_check(self) -> None: ...
```

`LoginAttemptRepository.record_failure(subject_type, subject_id, *, max_attempts,
locked_until)` atomically increments the stored count and sets the lock when that count
reaches `max_attempts`. `locked_until` is the candidate expiry, even below the threshold.
The returned `LoginAttempt` contains the stored count and lock expiry; providers must
use that row for their lock decision. A failure preserves an existing lock. A threshold
of one locks on the first insert. Custom adapters must implement this contract; no
schema migration is required.

- Services receive a `Storage` object and never import an adapter.
- No hard deletes in v1: deactivation sets `is_active` to false.
- Duplicate keys raise `AlreadyExistsError`. Missing records return `None`, and services decide whether that is an error.

## SQLAlchemy adapter

Installed with `pip install tenantkit[sqlalchemy]`. Uses SQLAlchemy 2.0 async.

- **Shared connection:** the host passes its own `async_sessionmaker`. The adapter never creates an engine.
- **Table prefix:** configurable, default `mt_`, giving tables like `mt_tenants` and `mt_admins`. No schema name option in v1.
- **Own metadata:** the adapter's tables live on their own `MetaData` object, exposed as `tenantkit.storage.sqlalchemy.metadata`.
- **Dynamic fields:** `attributes` is a JSON column (JSONB on PostgreSQL). Validation happens in the control plane before writing.
- **Constraints:** unique index on tenant slug, on admin email, and on email for tenant users (global, not per tenant). Foreign key from tenant users to tenants.
- **Transactions:** `storage.transaction()` wraps a session transaction, so multi-step operations either fully succeed or fully roll back.

```python
from tenantkit.storage.sqlalchemy import SqlAlchemyStorage

storage = SqlAlchemyStorage(session_factory=async_session, table_prefix="mt_")
kit = TenantKit(config=config, storage=storage)
```

### Table summary

| Table | Columns | Indexes |
| --- | --- | --- |
| `mt_admins` | id, email, password_hash, roles (JSON), impersonation_mode, impersonation_tenants (JSON), is_active, timestamps | unique email |
| `mt_tenants` | id, slug, attributes (JSON), login_policy (JSON), is_active, timestamps | unique slug |
| `mt_tenant_users` | id, tenant_id (FK), email, password_hash, roles (JSON), is_active, timestamps | unique email; index on tenant_id |
| `mt_login_attempts` | subject_type, subject_id, failed_count, locked_until | primary key (subject_type, subject_id) |

## Migrations with Alembic

The package does not run migrations itself. The host includes the adapter's metadata in its own Alembic setup, so tenantkit tables are migrated with everything else.

```python
# alembic/env.py in the host app
from app.models import Base
from tenantkit.storage.sqlalchemy import metadata as tenantkit_metadata

target_metadata = [Base.metadata, tenantkit_metadata]
```

- The host runs `alembic revision --autogenerate` after installing or upgrading tenantkit.
- Release notes for each tenantkit version list any table changes.
- The table prefix must be set before the first migration and not changed afterwards.

## In-memory adapter

`tenantkit.storage.memory.InMemoryStorage` keeps everything in dictionaries. It enforces the same uniqueness rules and passes the same contract tests. It is for tests and local prototyping only.

## Writing a custom adapter

A host using another database, such as MongoDB, implements the `Storage` protocol and runs the contract suite against it:

```python
from tenantkit.testing import StorageContract

class TestMyStorage(StorageContract):
    async def make_storage(self):
        return MyMongoStorage(...)
```

## Error cases

| Error | When |
| --- | --- |
| `AlreadyExistsError` | A unique field (slug, email) already exists |
| `StorageError` | Any other database failure, wrapping the original exception |
| `StorageUnavailableError` | The health check fails at startup |

## Test cases

- Contract suite: create, read, list, update, and deactivate for every repository.
- Uniqueness: duplicate slug and admin email are rejected, and a tenant user email already used in any tenant is rejected.
- Transactions roll back fully when an error is raised inside them.
- JSON attributes round-trip without loss, including nested values.
- The SQLAlchemy adapter passes the contract suite on SQLite and PostgreSQL.
- Autogenerate with Alembic picks up all tenantkit tables, using the configured prefix.
- The adapter works with a session factory supplied by the host and never opens its own engine.

## Decisions

1. Tenant user emails are globally unique, so one person belongs to one tenant only. Only an admin, through an impersonation token, can act across tenants.
2. The table prefix alone (default `mt_`) is enough. No schema name option.
3. Async SQLAlchemy only in v1. A sync adapter is deferred.
